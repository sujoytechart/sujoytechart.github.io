Carrier Risk Platform: score risk with what was knowable

In progress

I am building an end-to-end platform to help freight brokers assess carrier safety risk before dispatch. The finished system will turn FMCSA inspection and crash histories into reproducible features, trained risk models and an API for scoring, using only information available at each decision date.

2Federal event feeds 2Time checks per historical feature

Target design: inspection and crash histories, filtered by both event date and reporting date.

The design preserves immutable snapshots and corrected event versions, makes loads idempotent, and tests historical features for future-data leakage. Training labels become eligible only after their outcome window has elapsed.

PythonAirflowdbt-corePostgresSnowflakeMLflowFastAPITerraformAWS
Why event time alone cannot prevent leakage

A crash may happen before a scoring date but appear in federal data weeks later. Filtering only by event date would let the model use information that was not yet available. The design checks both dates and preserves corrected versions so historical predictions can use the record knowable at the time. Present-day carrier attributes are excluded where no historical archive is available.

  1. Ingestimmutable FMCSA snapshots
  2. Model dataversioned history + features
  3. Trainmature labels + MLflow
  4. Serverisk scores through FastAPI

Pipeline orchestration

Parallel pipeline routing: remove the shared failure domain

OracleClick to expandClick to collapse⌄

I removed a shared failure domain where one failed branch stalled every dependent job. Moving fan-out upstream to a component that already tracked each file’s interval and unit turned serial coupling into independently routable parallel branches, with source lineage preserved.

3Cadences: 15 min, hourly, daily2Routing keys: interval and unit

Routing scope spans 15-minute, hourly and daily data, with separate paths selected by interval and unit.

Each branch receives its own manifest and execution trigger, separating failure handling across routes. Dependencies still preserve processing order within each branch.

PySparkOracle ADWObject StorageGitLab CI/CD
Why routing happens before execution

The initial design put several branches under one event. Testing showed that one failed job could stop the entire event. Splitting the work before execution gave each route its own trigger. GitLab delivered the artifacts and configuration, while the routing stage and storage events handled runtime orchestration.

  2. Groupinterval + unit
  3. Manifestone object per route
